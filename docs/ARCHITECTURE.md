# Architecture

Follow Money is a single Android application module using Java 17, native views and SQLite. It has no application backend or network client.

## Shared UI foundation

`res/values/colors.xml` owns the light/dark semantic colors used by XML widget themes and the immutable `UiTheme` runtime palette. The app's existing dark-mode preference selects the palette. Brand/logo plates keep their authentic colors; they are not interchangeable with semantic surfaces. `UiTheme` also names the initial typography, spacing, radius and 48dp minimum touch-target tokens. Small income text uses a darker light-mode shade for contrast.

`UiComponents` supplies labeled fields, primary/secondary/destructive buttons, icon buttons, page headers, a centered amount field, horizontal native radio choices and account-choice cards. Fields grow with font scale, captions use `setLabelFor`, and custom backgrounds include keyboard focus and pressed feedback. Choice strips scroll horizontally at large font sizes instead of compressing labels; native radio buttons expose checked state. Account cards expose one named Button action and hide decorative children from accessibility. Framework Views expose native accessibility roles; ARIA is not used.

`UiSheets.prepare` retains the actual `AlertDialog`, its button references and callers' show/cancel/dismiss callbacks. It positions the window at the bottom, caps its content height, and places the same native buttons in a vertical footer. Validation installed by `setOnShowListener` can still keep a form open; dynamically revealed neutral actions remain available. `SystemUi` can apply insets to either an Activity window or a dialog window. The centralized `ChoiceDialogBuilder` uses this shell, retaining indexed search and selection state. Forms still awaiting migration temporarily use the sheet presentation.

`UiPages` holds a small form stack inside `MainActivity`. Each page owns a route, original values and mutable draft model; redraw never recreates an attached form. Header and system Back share a dirty-check confirmation. A page can explicitly opt into saved-state restoration of its editable model, scroll and input selection; non-restorable pages truncate that saved prefix. Never opt password/evidence forms into saved-state persistence without a separate privacy review. Consumers are display-name editing, transaction add/edit, transaction filters, bulk category review, source creation/bank correction and card/account linking. Existing parent navigation/filter/scroll state remains owned by MainActivity. Incoming intents pass through the same discard guard before leaving a form. A successful save pops the page before running any follow-up offer, so merchant-learning prompts cannot render behind the form.

`TransactionFormPage` uses primitive/String Bundle values, including source IDs and the original stored timestamp/precision. It never serializes bank message evidence. Kind changes preserve draft choices while hiding inapplicable category/destination controls; only transfers persist a destination. Save uses the existing manual-entry and `TransactionMutation` paths, retaining amount, source/destination and merchant-learning validation. Edits combine the chosen day with the original stored clock and leave precision unchanged; date-only records show an explicit date-only caption. New manual entries retain the existing save-time clock behavior. Existing archived sources remain available when editing their transactions. Filtering stays local until Apply; explicit Clear preserves the existing search and chosen period. Bulk review keeps an explicit snapshot of transaction IDs and delegates category-only updates to the existing DB method. Split bills and other financial-linking forms still use the shared sheets and have not migrated to pages.

`SourceFormPage` separates the bank (`payment_sources.name`) from the optional friendly label (`display_name`) and last digits. Creation requires a bank containing letters for account/debit/credit-card types; legacy numeric labels are preserved as friendly labels until the user edits them. There is no bank inference from card digits. `SourceMutation.correctBank` owns one transaction, rejects missing rows, alias collisions and bank changes on confirmed relationships/settlements, preserves IDs/old aliases/financial rows, and creates a new alias only when unowned. Profile-only changes can keep the original bank. Source kind and last digits remain unchanged during correction; this is not a general identity merge. The original three-argument creation API retains its duplicate-alias behavior for existing callers.

`SourceLinkPage` shows the selected identity and candidate debit cards/accounts with up to three recent transactions for that exact ID (including incoming own transfers). Activity is for recognition, never proof of a relationship. Candidates with unknown/different banks or archived status stay visible with a reason and bank-correction action. Correction returns to the same draft selection page and never links automatically. Review names the card/account and any existing relationship; confirmation revalidates through the existing link primitive. A not-sure action leaves without changing relationships. Credit cards retain a separate repayment flow. Incoming saved state contains only source IDs/edited source fields, never the recognition transactions or original messages. `finishThrough` closes a committed flow or an explicit not-sure exit without a discard prompt.

`tools/run-unified-ui.ps1` builds only the isolated `.cardreview.journeyqa` emulator package (default device 5556, separate from the user's 5554), checks source correction/linking, transaction pages, drafts/recreation/discard/save and native sheet validation/neutral buttons/date-picker return, and captures light/dark/200% font screenshots. It restores the emulator font setting in `finally`. `-Modes` can run a focused subset. Run the existing selection, period, card, reimbursement and SMS-import suites alongside it after changing shared controls. Automated node visibility checks and screenshots do not replace manual TalkBack or keyboard traversal acceptance. Remaining account surfaces, searchable settings and other financial journeys are subsequent migration work; this batch does not declare the whole UI migration complete.

## Data path

1. `SmsReceiver`, `SmsImportActivity` and `PaymentNotificationListener` receive supported sources; the user can also add or share text manually.
2. `ExpenseParser` and identity helpers extract conservative event, amount, currency and account information. An ambiguous input may remain unrecognized or require review.
3. `ExpenseDb` stores transactions, account identities, commitments, corrections and source associations. `EvidenceVault` protects stored source text using Android Keystore.
4. `RepairRules`, `MoneyTotals`, `MoneyFlow`, `DailyAllowance` and `Insights` derive summaries from the ledger and confirmed relationships.
5. `MainActivity`, widgets and reminders display the derived state. Changes trigger the relevant refreshes.

Consult class definitions for field and migration contracts; database schema numbers in historical notes are not authoritative.

`AppResources` owns the process-lifetime helper borrowed by `MainActivity` and its background jobs. It constructs that helper with the application context; Activity destruction never closes it. Other callers' explicitly scoped helpers retain their own try-with-resources ownership. `CaptureQueue` delegates to the process-owned serial writer: live captures, ledger normalization, historical SMS apply, CSV apply, merchant refresh and background repairs share it. A separate two-thread I/O pool handles preview, SMS scanning and reports. Activity callbacks check finishing/destroyed state on delivery; repair success preferences are saved on the worker after success even when the screen has gone. Queued jobs may retain their initiating screen until completion; screen/use-case decomposition remains pending. Existing synchronous UI mutations and separately scoped receiver actions still require later extraction. These in-memory workers provide no recovery after process death and no broadcast deadline guarantee; long imports can delay captures. Durable intake/retry remains separate Phase 3 work; the committed revision is described below.

`tools/run-resource-lifetime.ps1` builds a separate `.lifetimeqa` emulator app and verifies a worker transaction survives real Activity destruction, stale UI results are dropped, a replacement Activity reuses the helper, and configuration recreation preserves ownership. CI runs it after the existing SQLite suites and retains its output. It does not access a physical phone or prove SMS delivery/process-death recovery.

`CaptureRequest` carries the existing live source identity, text, capture timestamp and optional safe receipt alias. `CaptureTransaction` orders storage capture, bounded repair and an immutable `CaptureResult` using request-local observations, without reading the helper's `lastCapturedId`/`lastCaptureEvent`. Repair reports carry merge aliases so a removed incoming leg follows its outgoing row even if a fee reuses its numeric ID. The old accessors remain compatibility views for boolean callers. `accepted` retains their original meaning; `dbChanged` reports a committed, observed revision difference, including evidence-only and balance-only writes. It is a global invalidation signal, not a count attributed to this capture under concurrent writers. Live producers use it for refresh and require `COMMITTED` before notifications. IDs distinguish the initially inserted row from the surviving matched row; `transaction` remains the created-row notification snapshot. Reasons describe the storage branch, and evidence outcomes describe only the known write/body presence, without diagnosing encryption failure or asserting decryptability. `needsReview` reflects the matched row/event's stored review state, not all side effects.

`ExpenseDb` still owns the existing storage transactions. A caller-owned transaction returns `PENDING_CALLER`, with in-flight IDs/revision and `dbChanged=false`; it is not a commit receipt. Standalone live storage and repair are still separate transactions: bounded repair retains its legacy catch/rollback policy, but now reports failure. Capture returns `COMMITTED_REPAIR_FAILED` for that case, retains the committed capture's ID and change signal, and suppresses success notifications while refreshing persisted state. Rolled-back repair aliases are discarded. Storage/commit exceptions still propagate without a result. Boolean timestamp-aware calls now also construct the result snapshot while retaining acceptance semantics. Historical SMS import keeps its separate batch transaction, receipt policy and explicit cancellation confirmation. No durable intake, transaction ownership, schema or financial policy change is included. [Synthetic fixtures and contract limits](refactor-plan.md#p2-a-capture-contract-and-synthetic-baseline).

`ImportBatch` owns the historical SMS selection and bounded-repair transaction previously implemented in `SmsImportActivity`. In the normal activity-owned call, its returned net ledger increase follows commit; storage/repair failures propagate before the activity writes success preferences. The activity retains scanning, selection, progress, post-commit review reads and refreshes. Its static batch methods remain compatibility facades for existing callers/tests. The extracted selection path retains the prior nested transaction semantics; historical cancellation still requires explicit confirmation. No background scheduling or storage policy changes accompany this extraction.

`TransactionMutation.update` borrows the editor's `ExpenseDb`, requires ownership of its outer transaction and returns an immutable `MutationResult` after that transaction ends. It distinguishes an updated primary row from a missing row or an unapplied update. Only a successful primary-row update may teach a merchant rule; both writes share the transaction. Exceptions propagate and the connection remains with the caller. The editor retains its input and displays a no-change message when the row disappears while it is open; it reports success and closes only after an applied edit. Lower storage guards and nested edit transactions execute through the `ExpenseDb` facade and `TransactionRepository`; public void update methods remain compatible. Deletion policy, scheduling and the remaining mutation APIs are separate work.

`TransactionRepository` owns the existing transaction list, candidate, count, single-row and period queries, plus primary-row update, deletion and dependent cleanup. It borrows the same `ExpenseDb` connection and maps the same columns into immutable `ExpenseDb.Transaction` values; helper methods remain compatibility facades. The latest-500 cap, uncapped counts/candidate scan, period boundaries, caller-supplied time zone and each query's original ordering are preserved. Update counts, linked-card guards, statement-fee constraints, edit flags, exclusion/evidence handling and existing transaction boundaries are unchanged. Archiving reuses the same dependent-cleanup path; this extraction does not add delete/undo behavior. The helper now exposes the durable invalidation token described below; transaction queries do not own its storage.

`EvidenceRepository` records the existing capture-evidence values inside the caller's transaction and reads transaction/fee sources and commitment-observation history. It borrows the helper, retains conflict-replacement and source ordering, and uses the same `EvidenceVault` calls. Manual statement-fee descriptions, fee-parent lookup, unreadable-body flags, nullable legacy evidence and history limits are preserved. This move does not add encryption-failure states, change cryptography or create a plaintext fallback.

`AccountRepository` owns the existing account/source read queries, confirmed-parent grouping and source creation/alias/link/profile/merge/deletion primitives, plus manual/message balance snapshot storage, latest/history queries and the current-balance projection. Helper entry points remain compatible. Source alias counts, activity ordering, nullable parent/profile fields, account/card filters, labels and last-activity calculations are unchanged. Transaction grouping uses the same period query and adds a confirmed transfer to each distinct participating account once; it never infers a same-bank card relationship. Balance projection retains the same confirmed-parent grouping, currency isolation, event/receipt cutoff, insertion-order tie-break and `BalanceTimeline` deltas. Anchor metadata, confirmed/estimated status, history limits, negative-snapshot refusal and duplicate-key correction are preserved. The repository borrows the caller's helper/transaction and never closes or commits it. Automatic message parsing/source inference and schema migrations remain separate; this move adds no new atomicity or reconciliation policy.

Schema v21 adds nullable `transactions.time_precision` (`exact` or `date_only`). The v20 upgrade only adds the column; legacy rows remain null, including on re-import. `ExpenseParser.eventTimeWithPrecision` records the precision of the timestamp chosen at capture: an explicit date without a clock is `date_only`, an explicit clock or receipt-time fallback is `exact`. The latter does not prove a bank-stated event time. New CSV rows have date precision. UI list/detail/import preview labels date-only rows instead of showing their internal placeholder clock. Reimbursement selection, preview and confirmation use the same day-based eligibility when either endpoint is date-only; unknown legacy precision retains the prior timestamp rule.

`ExpenseDb.mergeEntries` moves reimbursement endpoints, fee-parent references, recurring origins and source evidence inside a transaction. Conflicting repayment targets/allocations or fee parents leave automatic copies marked for review. Own-transfer reconciliation rejects repayment-linked rows before changing their kinds. Historical import reports an uncapped net ledger increase, distinct from the number of processed SMS.

Capture notifications use private visibility and a generic public version; hidden amounts also remove merchant/card details from the private notification. CSV text columns prefix formula-like values with an apostrophe and escape quoted fields. Numeric amount columns stay numeric. Spreadsheet save/reopen behavior is not a universal security guarantee, and re-import retains the protective apostrophe as text.

`CommitmentRepository` owns the existing recurring-plan insert/update/list/lookup, due-day/reminder-setting, removal and alerted-date primitives, plus legacy early-payment normalization and paid/finish/reopen state writes. `ExpenseDb` retains compatible entry points and the same `Recurring` read model. The moves preserve columns/null mapping, active-before-done/due ordering, duplicate handling, trimming/defaults, paid-count clamping, completed-status preservation, due-day bounds and alert resets. The four state methods retain their existing bodies, cycle windows, due-date anchors, payment-gap guards, covered-due metadata and update-return behavior. They borrow the caller's helper/transaction and introduce no transaction, commit or close. Normalization still scans all plans, including when called before a missing-ID payment request; without a caller-owned transaction the multi-step work has no newly added atomicity guarantee. Named-payment and amountless service matching delegate to `CommitmentMatcher`; settlement identities, linked-edit recalculation, use-case/result boundaries and future cycle policy remain separate work. This does not complete the commitment domain or Phase 2.

`CommitmentMatcher` owns the existing `advanceRecurring` and `markServicePaid` bodies through private `ExpenseDb` compatibility facades. It borrows the helper and delegates recurring reads/state writes to the existing repository facades, adding no SQL, transaction, worker or close. Named matching preserves the one-minor-unit tolerance, same currency, twelve-day window, generic/review/done exclusions and exactly-one-match guard. Service receipts retain their original all-eligible-plan loop without amount/currency disambiguation; this extraction does not make that policy safe or implement cycle settlements. `matchCommitmentMessage` remains an unwired prototype in `ExpenseDb`, and transfer-to-commitment matching/classification remains there unchanged. No parser path is connected or newly accepted by this move.

`ReimbursementRepository` owns the existing repayment-link guards/lookups, offset projection, link/relink, exact undo and unlink primitives. `ExpenseDb` remains the compatibility facade and retains the `ReimbursementPreview` value and `effectiveAmount`; candidate selection, preview and confirmation are delegated to `ReimbursementUseCase`. The repository uses the borrowed helper and existing transaction lookup; it preserves the original link transaction, including nested use from confirmation, and adds no helper close. Chronological clipping, currency/kind/missing-row guards, nonpositive-link handling, linked-income reads and failed-relink rollback are unchanged. Gross ledger rows and persisted legacy links are not rewritten by projection. Relationship SQL inside merge/archive/delete flows remains with those owners for later extraction; this slice adds no new atomicity, result contract or repayment policy and does not complete Phase 2.

`ReimbursementUseCase` owns the existing same-day/older purchase selection, timestamp-precision eligibility, read-only preview totals/fingerprint and confirmation orchestration. It borrows `ExpenseDb` and delegates data access through the existing repositories' facades. Confirmation retains its original transaction and stale-preview recheck; the repository's nested link transaction is unchanged. Public helper APIs, the exact one-minute tolerance, date-only day comparison, candidate ordering, currencies and open-transfer exclusions remain compatible. This extraction does not change endpoint-read timing inside direct linking, optimize offset projections, add a post-commit result contract, or implement linked-edit settlement policy; those remain separate work.

Schema v24 adds a single-row `ledger_revision` and INSERT/UPDATE/DELETE triggers on all 24 application data tables. The token is an invalidation generation, not a financial event count: matching-row updates can advance it even when values are equal. It advances inside the writer's SQLite transaction, rolls back with failed work, survives helper/process reopen and remains monotonic through delete-all-data; reads, ignored inserts and zero-row writes do not advance it. Existing `changes()` callers read this database-wide value. The v23 upgrade installs only metadata/triggers without rewriting user rows, evidence or financial rules; future data tables must join the tracked list, checked against the live schema in instrumentation. This does not add durable capture intake or recovery for undelivered sources.

`MainActivity` stamps a worker snapshot before its reads and rechecks both local generation and the committed revision at UI delivery. A concurrent commit rejects the old snapshot and queues a fresh pass; a different applied revision forces redraw even when expense-only suggestions match. Existing editing-surface guards preserve drafts. Render/resume and existing post-commit broadcasts discover changes by other helpers; a missed broadcast can therefore be recovered at the next refresh. This does not promise realtime redraw without a refresh signal, a durable job-result channel, or a measured UI latency improvement.

Refused-fee repair preflight sets the debit's `needs_review` marker only while it is zero. Rechecking an already marked refusal therefore performs no marker write or revision increment. A cleared marker can still be set again and rolls back with its caller; removing the fee blocker still permits normal reconciliation. Other writes in a repair pass can independently advance the revision; this guard does not change fee eligibility or consent policy.

## Financial boundaries

- Amounts use integer minor units. Aggregation stays within a currency.
- An account balance starts from an explicit statement anchor when available. Later adjustments are estimates and must be labeled.
- Transfers between confirmed own accounts do not become income or spending. Unknown transfer recipients need review.
- A scheduled installment is a future obligation. Creating a plan does not create a paid transaction.
- Reimbursement/refund links adjust eligible spending and incoming money, while preserving the linked records. Do not erase the source transaction to fix a summary.
- Daily allowance is a user-defined limit. Salary or incoming transfers do not automatically enlarge it.
- Source deduplication and financial reconciliation are separate: nearby payments are not proof of duplication.

## UI and support

Settings is organized by task: budgets/widgets, capture, appearance/profile, reminders, data/privacy, and help. Financial review tools are kept under Data and Privacy. Assets/debts shortcuts appear only when there is existing data in those modules.

`GitHubSupport` constructs browser URLs using encoded fields. The user reviews device metadata before opening a bug form. No issue is submitted automatically, and no financial data is included in that metadata.

## Transaction journeys and daily points

`TransactionJourney` preserves the parent detail chain. `MainActivity` keeps bounded scroll positions by screen/query/filter context and saves them, transaction parents and drilldown return targets in the activity state bundle. A transaction edit finishes in the same details screen. Budget and points drilldowns return to their initiating dialog.

Reimbursement candidates default to the incoming transaction's local calendar day, sorted by timestamp/id descending, without an eight-item cap. An explicit older-purchase branch includes eligible earlier records. `previewReimbursement` is read-only and projects the purchase day's living total; `confirmReimbursement` rechecks the preview under a transaction. Undo deletes only that exact income/expense/amount link. Gross ledger records remain unchanged.

The native picker is a bottom-aligned dialog with selectable cards, checked-state accessibility, a scrollable candidate area and a separate review button. Returning from the impact preview retains the selection and search. Incoming transaction rows and details derive a personal-share caption from valid effective reimbursement offsets, including all repayments against that purchase; they retain the gross incoming amount.

`DailyPointsStore` stores opt-in, the first observed daily limit per currency/date and explicit coverage confirmations in local preferences; it never writes transactions or cached score totals. No historical budget anchors are inferred. `DailyPoints` derives each day's points from `(limitMinor - effectiveLivingMinor) / 1000` using `BigDecimal`, then rounds to a whole number with `HALF_UP` (ties away from zero). The balance sums those rounded daily awards so it matches the visible history. Only closed, coverage-confirmed dates without review-flagged rows contribute; today remains provisional. Edits/refunds recompute the relevant purchase-date score using its anchored limit. Coverage is a revocable user assertion of complete recording, rather than a guarantee of bank/SMS coverage. Disabling keeps the history; deleting all local data also clears points preferences. The points summary separates the confirmed balance, yesterday and provisional today; the next 100-point milestone is visual encouragement only, not a monetary reward. History and calculation guidance are separate from the initial summary.

`JourneyUiTest` is restricted to an emulator and the separate `.journeyqa` package. It exercises real dialogs and Back using a synthetic private database, including preview/cancel/confirm/undo, related-detail parents, search scroll restoration and points review/coverage. Captures stay local and ignored.

`AuditRegressionTest` runs with `-e feature_audit regressions` on a disposable emulator. Its isolated fixtures cover merge relationships/conflicts, own-transfer rejection, imports above 500 rows and rollback, notification privacy, CSV escaping, time eligibility and the frozen `androidTest/assets/schema-v20.sql` migration fixture. These are functional database/view-construction checks, not full visual or physical-device acceptance tests.

`UpgradeInstallTest` is a separate instrumentation runner for a fresh `.upgradeqa` install. Its `seed` mode runs with the archived v20 APK; after an in-place APK update, `verify` compares all old ledger columns, financial preferences, encrypted and decrypted evidence, repayment effects and points, checks null legacy precision/integrity, and opens the real updated activity. `ReleaseVisualTest` runs with `-e feature_audit visual` only in `.releasecheck.journeyqa`, captures native light/dark views, a compact RemoteViews preview and a posted notification, and generates a synthetic CSV through the actual export callback. SystemUI screenshot review and local Excel opening are separate manual checks. QA binaries, snapshots and captures remain local and ignored.

## Monthly summaries

`MonthlyReport` derives closed-calendar-month totals from the same effective `MoneyFlow.Item` amounts as Analytics, with separate currency summaries and explicit behavior thresholds. Coverage confirmations are keyed by currency/month and hashed effective rows; changed imports, edits or reimbursements invalidate the relevant confirmation. An empty or zero prior denominator never produces a percentage.

`MonthlySummaryReceiver` uses an inexact local first-of-month alarm from 09:00 and catches up on activity resume, date/time changes and reboot. It stores the start, latest notified and latest seen months in local preferences. Notifications contain no amounts or merchants, require system permission/channel availability and recorded activity, and deep-link to the completed month. Reading hides the home entry while retaining the Analytics report. This scheduling does not promise delivery while Android force-stops or restricts the app.

## Widgets

`LockSummaryWidget` is a separate transparent, compact provider for compatible widget hosts. It reads `DailySummary`, the selected widget currency and the existing hide-amounts preference; it has no independent financial calculations or persistent settings. `SummaryWidget.refresh()` includes its installed instances in existing refresh paths. It displays only an exact two-decimal remaining/overage value and caption, clears values and accessibility text on unavailability, and opens the app through a normal immutable PendingIntent. The host owns placement, padding and the notification region. The three existing home widget layouts retain their presentation.

## Cancellation history and credit-card repayments

Schema v22 adds `capture_events`, `card_settlements`, and `card_settlement_allocations`. Active transaction and total queries are unchanged. Explicit bank cancellations archive the matching debit and its dependent fees, preserve both encrypted debit/cancellation evidence, and create a visible non-financial event. Old cancellation archives are backfilled without inventing missing source text; an unreadable legacy archive payload no longer blocks the upgrade: its exact payload is kept and an explicit canceled event with unavailable details/unknown amount is shown.

Schema v23 adds nullable `capture_events.display_at` with index `(display_at DESC,id DESC)` and table `sms_import_receipts(unique_key)`. `display_at` is the archived operation date when readable, otherwise the receipt/archive time; v22 rows are backfilled once. Timeline reads filter and order by this indexed column in SQL. Import receipts record every processed historical SMS hash (including balance-only and hint messages) and are cleared by delete-all-data. An existing "recorded" notification is replaced by a privacy-aware cancellation notice; its destination is an immutable event ID, separate from reusable transaction row IDs.

Matching requires a single outgoing transfer (or an expense already classified as a transfer) with the same bank/source identity, currency and gross amount, a receipt timestamp within the preceding two minutes, readable original debit proof, no conflicting bank reference, and no reimbursement links. Fee children are not candidates. Edited rows are protected, except explicitly confirmed card settlements. Ambiguous/unmatched cancellations remain visible and do not change totals. Ambiguous eligible rows can be selected and reviewed manually; confirmation rechecks source identity and all matching conditions. Bank-confirmed repayments with a linked transfer fee are rejected with an explicit explanation; fee-bearing repayments are not supported and the transfer/fee rows stay unchanged. Repeated messages are idempotent; an earlier debit arriving after its cancellation is reconciled using source timestamps. Identical bank aliases use the same cancellation fingerprint.

`CardSettlements` requires explicit account/card selection and review, revalidates the preview inside a database transaction, and changes only the selected outgoing debit into an own transfer. Optional allocations link that transfer to prior purchases on that exact credit card in the same currency, capped by outstanding gross purchase cost. Date-only rows use calendar-day eligibility. The unallocated remainder remains visible on the card repayment; it never becomes an invented fee. Undo restores the debit's original classification/source and removes only its allocations. A canceled confirmed repayment releases allocations without deleting the original card purchases or statement fees; the archived repayment retains its allocation payload.

Statement fees are explicitly entered and confirmed from a statement, in the purchase currency and on its purchase day. They inherit the purchase's card/category, retain the user's description as manual evidence, and have date-only precision. There is one statement-fee entry per purchase; an identical retry is idempotent. This flow does not infer tax, exchange rates, fee amounts or a fee time from a bank balance. Linked purchases/repayments/fee rows cannot be edited/deleted or merged until allocations are undone; related source identities cannot be deleted/merged while a repayment is linked. Re-import cannot rewrite allocated purchases. Purchase and repayment allocations never reduce gross consumption a second time.

The card journey reuses the reimbursement bottom-sheet window and existing typography, theme colors, rounded surfaces, account labels and buttons. Account/card selection uses logo-bearing radio cards with type and last-four labels rather than native dropdowns. It preserves selection when returning from review and provides a result/undo step. Cancellation events are interleaved with active transactions by the archived operation date, with an × icon, canceled badge and struck-through amount. Archived kind/category/account metadata participates in filters; unresolved notices use their receipt date and do not impersonate a ledger row. Canceled rows are excluded from totals and bulk editing. Legacy records without readable operation metadata fall back to an explicitly labeled archive/receipt timestamp. Timeline reads include cross-month cancellations and are not capped at 100 events. The original SMS may be unavailable for a legacy archive or after device key loss; that limitation is displayed rather than guessed.

Synthetic regression: a card purchase of 220.00 plus a confirmed statement fee of 6.60 is allocated 226.60 from a repayment of 227.00; 0.40 remains unallocated. Cancellation archives the repayment, retains both source messages, and reopens 226.60 of purchase cost. A successful last-contactless-use warning is not a decline; a real rejection is never booked as spending. No real phone ledger rescan, repair, installation or release artifact modification is part of this change.
